Demand prediction ML · SKU level · weekly forecast origins

How this repo fits together

The project has two halves that look alike and do opposite things. One scores the past — seven models, three boards, a dozen studies, all reading finished targets. One buys for the future — a single path from forecast.py to an order quantity someone spends money on. They share a dataset builder and exactly one hand-off.

The spine

Every box, and what moves between them

Trap one

Why there are two dataset files

Both come out of prepare_data.py in the same pass, from the same expressions. They are not a copy and a subset — they are disjoint, and building serving features anywhere else is how train/serve skew gets in.

Trap two

The buy window sits past the evidence

Models are trained at 30, 90 and 180 days. Nobody buys on those numbers — you buy on lead time plus review period. When that window runs past 180 days, every order quantity rests on an extrapolation nothing was trained on.

Module reference

Who is connected to what

The actual coupling is simpler than the file count. Every file in dev/ imports dev/common.py; common.py imports only demandml.config, demandml.metrics and demandml.splits. The seven model files import nothing but common (plus lgbm_core, which is a shared estimator, not a model). Cross-imports between siblings are rare and deliberate: policy → economics, forecast → events, window_backtest → policy.

Core library — src/demandml/

ingest · clean · panel

Raw CSV to a daily SKU panel. Drops the partial last export day and the leaky rolling averages the export ships.

features.py

Lags and windows, all .over(SKU). Owns the banned-column set — anything measured on the target day lives there, not in the matrix.

splits.py

Rolling origin with a horizon-sized gap. Random k-fold scores far too well on a panel like this.

metrics.py · config.py

WAPE, bias, the cost metric, and the path/constant surface every entry point reads.

Dataset + shortlist — model_lab/

prepare_data.py

Builds both dataset files, the ly_* year-ago columns and the y_cum_m1..m6 month slices. The one place serving features may be built.

compare_models.py

The full-field board. The seven in dev/ were shortlisted out of here.

segment_report.py

WAPE by line, marketplace, volume band and Syntetos-Boylan quadrant. Read it before quoting a catalogue-wide bias — lines with opposite biases cancel.

The buying path — dev/

forecast.py

Units over the next 30/90/180 d per SKU. Emits demand, never an order quantity — the panel has no stock or on-order, so there is deliberately no order_qty column.

policy.py

Forecast to order quantity. Interpolates the cumulative forecast onto lead time + review, rounds MOQ and cartons up, routes recovered SKUs to a review file.

economics.py

One cost ratio per SKU, anchored so CU:CO sets the level. The anchoring cancels three unsourceable assumptions exactly — and a measured per-SKU storage term would break that cancellation.

inventory CSV

On hand and on order per SKU, passed to policy.py as --inventory. The sample data ships one; without it order_qty stays null by design.

events.py

The only place human judgement enters. Expected effect only, gated on entered_at. With no file the adjustment is exactly 1.0× + 0.

coverage.py

Which catalogue SKUs the plan does not answer for. policy.coverage_gap delegates here so the plan and the report cannot disagree.

Boards and search — dev/

cost_board.py

Ranks on inventory cost from cached predictions. Read this, not the WAPE board, before anyone makes a purchasing decision — the two disagree about who is first.

compare_models.py · dashboard.py

The WAPE board and its report; six panels per model plus four cross-model charts, never refits.

tune.py · compare_tuning.py

Search cut at the earliest fold's train_end, so it can never score a test row. A tuned model is allowed to come out worse, and the report says so.

The studies

Files that ship a verdict, not a number

These sit off the spine. Each reads cached results, answers one question and writes one markdown file. They change what you believe, not what gets ordered.

regime.pyRead this before trusting any bias number here. A "systematic under-forecast" seen on a few folds can be an artifact of one demand regime — over many folds average bias sits near zero while the fold-to-fold swing is far larger.
debias.pyThe bias is a shape, not a level. The global multiplier captures most of the gain; everything past it is small and flips sign by horizon.
calibration.pyShould the multiplier be one number? Per-SKU can win at short horizons and lose at 180 d, because a SKU has about one non-overlapping window there. Granularity is capped by evidence.
event_backtest.pyReplays recorded deals at the backtest origins. Cost barely moves, in either direction. The multiplier already prices in the average promo; enter only events with no precedent.
longhorizon.pyIs the flat-rate extension past 180 d good enough to buy against? Costs a little, but WAPE is essentially identical and the sign flips fold to fold. Not worth a fourth horizon.
window_backtest.pyScores the forecast at the window you actually buy against. Calls policy.interpolate_cumulative rather than reimplementing it, so it scores the real ordering path.
datacheck.pyDoes the input still look like the input this was built on? Quantiles, not means. Matters most in production use: a wrong input produces a plausible forecast.
track.pyThe only file that can catch train/serve skew in the open-origin path — a backtest stays clean when that breaks. Also scores the human overrides, not just applies them.

One codebase, three output sets

Everything in dev/ exists three times

common.set_mode() switches which half you are writing. Model files are never edited by tuning — their PARAMS stay put and tuned values arrive as keyword overrides at build time, so the baseline stays reproducible from the code as it stands.

FlagResultsFiguresWhat it means
(none)results/initial_figures/The models as their files are written. The reproducible baseline.
--tunedresults_tuned/tuned_figures/After tune.py picked hyper-parameters. Worse on cost for most models — do not adopt wholesale.
--costresults_cost/cost_figures/Rebuilt against inventory cost instead of WAPE. Only models declaring cost_params can honour it — today just lgbm_quantile. Cannot combine with --tuned.

DEMANDML_MODE pins one of these for a whole process, so a scheduled job doesn't depend on every entry point being passed the right flag. An explicit set_mode() still wins.

Before you change anything

The things that bite

  • A timing bug makes scores better. That's why tests/test_leakage.py exists — run it after touching features.py or splits.py, and test_tuning_isolation.py after touching tune.py or set_mode. Nothing else complains.
  • Stock-out days are censored, not zero. sample_weight = 0 on OOS zero-days. Scoring with keep_censored=True measures stock-outs, not demand.
  • WAPE is a reporting metric, not an objective. Its optimum is the conditional median, which sits below the mean on this panel. The cost-minimising forecast is the CU/(CU+CO) quantile, with the ratio set in assumptions.toml. Read common.target_quantile(), never hard-code it.
  • CU:CO is not a hyper-parameter. If it sits in tune.py's search space, a WAPE-driven search pulls the target below the median — i.e. decides, on nobody's authority, that a stockout is cheap. tests/test_cost_metric.py fails if it comes back.
  • A SKU with no stock record gets order_qty = null, never zero. Polars evaluates NaN > 0 as TRUE, so a NaN sentinel there silently orders a full window of cover for everything unmatched.
  • The multiplier map must reproduce the cost board. The optimal scalar is the cu/(cu+co) quantile of actual/predicted weighted by predicted — that falls out of the first-order condition. Weighting by actual over-orders the whole catalogue by several percent, and nothing else would notice.
  • A green CI tick is narrower than it looks. Two of the four leakage guards skip without data/processed/.
